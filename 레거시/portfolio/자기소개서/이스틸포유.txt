[철강 유통의 디지털 전환을 직접 만드는 곳, 제가 해온 일과 가장 잘 맞습니다]
이스틸포유는 포스코 계열의 철강 전문 온라인 거래 플랫폼입니다. 전통적으로 대면과 관계 중심으로 이뤄지던 철강 유통 구조를 디지털로 바꾸는 회사입니다. 단순히 철강재를 올려놓고 파는 쇼핑몰이 아니라, 경매와 정찰제 판매, 물류 연계, 금융 서비스까지 하나의 플랫폼 안에서 처리하는 구조입니다. 구매자가 제품을 선택하는 순간부터 결제, 물류, 대금 정산까지 여러 흐름이 맞물려 돌아가야 하기 때문에, 거래 정보의 정확성과 플랫폼 운영 안정성이 서비스 신뢰와 직결됩니다. 철강 거래는 단가가 크고 거래 이력이 중요한 도메인인 만큼, 플랫폼 오류 하나가 바로 신뢰 문제로 이어질 수 있는 환경입니다. 그래서 기능을 잘 만드는 것만큼 운영 중 발생하는 이슈를 빠르게 파악하고 성능을 안정적으로 유지하는 역량이 중요합니다.
저는 현재 현대위아에서 MES 운영 시스템을 개발하고 있습니다. 생산, 재고, 공정 데이터가 ERP·PLC 등 여러 시스템과 연계되는 제조업 환경으로, 철강처럼 데이터 정확성과 운영 안정성과 산업 도메인이 비슷합니다. 또한 애기야가자에서 커머스 플랫폼을 운영하며 트래픽 대응과 성능 개선을 직접 경험했습니다. 산업재 도메인과 커머스 플랫폼 운영, 두 가지를 모두 경험한 만큼 이스틸포유의 환경에 빠르게 적응하고 기여할 수 있다고 생각해 지원했습니다.


[빠른 조치보다 정확한 원인을 먼저 찾습니다]
운영 중인 서비스에서 문제가 생기면 빨리 고쳐야 한다는 압박이 옵니다. 해당 문제가 생기면 선 조치 후 문제의 흐름을 살핍니다. 운영 환경에서는 유사한 문제가 다른 형태로 반복되는 경우가 많았기 때문입니다.
애기야가자에서 이벤트 기간에 메인 화면과 이벤트 페이지 응답이 갑자기 느려졌을 때가 있었습니다. 서버 자원부터 늘리자는 의견도 있었지만, 저는 먼저 로그와 쿼리를 확인했습니다. 반복적으로 조회되는 데이터가 매번 DB를 타고 있다는 걸 확인했고, 해당 데이터를 Redis 캐시로 분리하고 저장 구조를 조정했습니다. 결과적으로 주요 API 응답 속도가 800ms에서 300ms로, 캐시 처리 성능은 129ms에서 24ms까지 줄었습니다.
현대위아에서도 같은 오류처럼 보여도 원인이 입력 데이터인지, 연계 시스템인지, 중간 처리 로직인지에 따라 대응이 달랐습니다. 그래서 문제가 생기면 항상 데이터가 생성되고 전달되고 반영되는 흐름 전체를 먼저 따라가는 방식이 습관이 됐습니다.
이스틸포유 플랫폼은 거래, 물류, 금융이 맞물리는 구조인 만큼 이슈가 생겼을 때 어느 구간에서 어긋났는지 빠르게 찾는 역량이 중요하다고 생각합니다. API, DB, 연계 구간 전체 흐름을 기준으로 원인을 찾고, 같은 문제가 반복되지 않도록 개선하는 방식으로 기여하겠습니다.

[운영 중에도 믿을 수 있으려면, 문제가 생겼을 때 원인을 찾을 수 있어야 합니다]
개발할 때 가장 중요하게 생각하는 것은 문제가 생겼을 때 원인을 찾을 수 있어야 한다는 것입니다.
해당 가치관은 경험에서 만들어졌습니다.
Click-CEO 프로젝트에서 WebSocket 전환 직후 Stress test를 돌렸을 때 연결 실패율이 44%까지 올라갔습니다. 처음에는 WebSocket 설정 문제처럼 보였습니다. 빠르게 조치하고 넘어가자는 의견도 있었습니다. 하지만 팀원들과 로그를 처음부터 다시 따라가 보니, 봇 주문 생성에서 Redis 적재, Kafka 처리로 이어지는 흐름 중간에 병목이 쌓이고 있었습니다. 화면에 보이는 증상만 봤다면 엉뚱한 곳을 고쳤을 겁니다. 원인을 찾을 수 있는 구조가 있었기 때문에 정확하게 해결할 수 있었습니다.
현대위아에서도 마찬가지였습니다. 여러 시스템이 맞물린 환경에서는 같은 오류처럼 보여도 원인이 입력 데이터인지, 연계 시스템인지, 중간 처리 로직인지에 따라 해결 방식이 달랐습니다. 그래서 기능을 만들 때부터 데이터 흐름을 먼저 보고, 어디서 어떤 로그를 남겨야 나중에 추적이 되는지를 함께 설계하는 방식이 자연스러워졌습니다.
세상에 완벽한 코드는 없다고 생각하기에 늘 오류를 마주쳤을 때 명확하고 쉬운 로그를 남겨 빠르게 조치 할 수 있는 코드를 만들어야 한다 생각합니다.

[현업과 협력사 사이, 중간 프로세스를 직접 만들었습니다]
현대위아에서 PM과 개발을 함께 맡으며 기존 이슈 처리 방식에서 반복되는 문제를 발견했습니다. 이슈가 생기면 현업이 협력사에 바로 전달하는 구조였는데, 현업은 화면 증상을 설명하고 협력사는 그걸 기준으로 수정하다 보니 실제 원인이 다른 시스템에 있는 경우 엉뚱한 지점을 고치는 일이 반복됐습니다.
저는 PM이면서 개발도 담당하고 있었습니다. 현업이 어떤 흐름으로 시스템을 쓰는지 알고, 내부 시스템 구조와 데이터 흐름도 알고 있었습니다. 이 두 가지를 연결할 수 있는 사람이 중간에 있어야 한다고 판단해, 이슈가 협력사에 바로 가지 않고 제가 먼저 검토하는 프로세스를 만들었습니다.
이슈가 들어오면 DB를 직접 조회하고 시스템 로그를 분석해 어느 구간에서 처리가 어긋났는지 추적했습니다. 원인이 정리되면 협력사에는 증상이 아닌 원인과 영향 범위를 기준으로 전달했습니다. 이후 현업에서 같은 이슈로 재차 연락하는 경우가 줄었고, 이슈 하나를 처리하는 데 걸리는 시간도 짧아졌습니다. 협력사도 원인이 명확하니 바로 작업에 들어갈 수 있었습니다.
도메인과 개발을 동시에 이해하는 사람이 중간에 있을 때 소통 비용이 가장 빨리 줄어든다는 걸 이때 배웠습니다. 이스틸포유에서도 시스템 간 이슈가 생겼을 때 현업과 개발 사이에서 원인을 정확히 정리하고 연결하는 역할을 하겠습니다.
