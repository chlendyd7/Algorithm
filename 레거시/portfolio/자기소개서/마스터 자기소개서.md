# 마스터 자기소개서

## 1. 핵심 경험 (기술/정량)

### 데이터 정합성
현대위아에서 운영 시스템을 다루며, 저는 데이터 정합성이 백엔드 개발자가 반드시 지켜야 할 기준이라는 점을 체감했습니다.
현재 제조업 환경에서는 AX 스마트 팩토리 전환을 시행하며 로봇, 생산, 품질 등 다양한 데이터들과 시스템들이 결합되어 진행되고 있습니다.
해당 데이터들은 단순히 조회되는 정보가 아니라 현업의 판단과 후속 시스템 동작의 기준이 되고 있습니다.
그래서 데이터가 잘못 집계되거나 전달되면 단순한 숫자 오류로 끝나지 않고, 잘못된 현황 판단이나 품질 이력 추적 실패 등 실제 크리티컬한 운영 문제로 이어지는 경우가 있었습니다.
저는 이 과정을 겪으며 문제를 눈앞의 화면에서만 보면 안 된다는 점을 배웠습니다.
다양한 시스템이 얽혀 있다 보니 비슷한 오류처럼 보여도 원인이 담당 시스템 뿐만 아니라 다른 시스템에서 넘어온 데이터이거나 중간 처리 로직에서 발생한 경우 등 다양한 케이스가 많았습니다.
이런 트러블슈팅 과정 속에서 개발을 할 때 데이터가 생성되고 전달되고 반영되는 흐름 전체를 먼저 확인하는 습관을 갖게 되었고, 문제가 생기더라도 쉽게 원인을 찾을 수 있도록 로그와 예외 처리를 함께 설계하는 방어적인 방식으로 개발하게 됐습니다.

### 대규모 트래픽
B2C 서비스에서는 대규모 트래픽을 견디는 구조의 중요성을 배웠습니다.
장소추천 플랫폼 애기야가자를 운영하던 중, 평소에는 문제없이 동작하던 기능들이 이벤트로 트래픽이 몰리는 순간 응답이 밀리기 시작했습니다.
메인 화면과 이벤트 페이지 로딩이 느려지면서 사용자 불편과 이탈률이 높아졌고, 이를 계기로 병목 구간을 직접 분석했습니다.
반복적으로 조회되는 데이터를 Redis 캐시로 분리하고 DynamoDB로 데이터를 이관해 조회 부하를 줄인 결과, 응답 속도를 유의미하게 개선할 수 있었습니다.
이 경험을 통해 백엔드 개발자의 역할은 기능을 구현하는 데서 끝나지 않는다는 점을 배웠습니다.
어떤 로직이 병목이 되는지, 어떤 처리를 어떤 저장소로 분리해야 하는지를 구조적으로 판단하는 역량이 결국 서비스의 안정성을 결정한다는 것을 직접 확인했고, 더 큰 규모의 트래픽을 다루며 이 역량을 더 키우고 싶다는 목표를 갖게 됐습니다.

### AI 역량
AI 역량과 관련해 가장 구체적인 경험은 현대위아에서 직접 설계하고 배포한 바이브코딩 스튜디오입니다.
claude Agentic Loop 기반으로 기존의 시스템과 통합하기 위한 MCP 도구를 직접 구현하고, CodeGenerator / EditAgent / SummaryAgent를 LangGraph로 분리한 멀티 에이전트 구조를 설계했습니다.
단순히 LLM API를 호출하는 수준이 아니라, AI가 어떤 도구를 어떤 순서로 호출해야 하는지를 구조적으로 설계하는 경험이었습니다.
SSAFY 프로젝트에서는 pgVector 기반 RAG를 직접 구현하고, 영상 리사이즈를 통한 토큰 비용 절감을 추론 파이프라인 설계 단계에서 반영했습니다.
AI 기능을 얹는 것이 아니라, 비용·안정성·확장성을 고려한 AI 서비스 백엔드 구조를 직접 설계한 경험입니다.

### AI 서비스의 블랙박스 문제
바이브코딩 스튜디오를 운영하면서 곧 한계에 부딪혔습니다. CodeGenerator, EditAgent, SummaryAgent 세 에이전트가 순차적으로 실행되는데,
실패가 발생하면 어느 에이전트에서 얼마나 걸렸는지, 어디서 토큰이 소비됐는지 로그를 직접 뒤져야 했습니다.
AI 추론 과정이 블랙박스 그대로였습니다.

### 에이전트 관측 시스템 구축
이를 해결하기 위해 에이전트 실행 전반을 추적하는 AgentOps Tracer를 설계했습니다.
에이전트 이름, 사용 모델, 응답 레이턴시(ms), 입출력 문자 수, 성공 여부와 오류 메시지를 매 실행마다 DB에 저장합니다.
핵심 설계 원칙은 메인 흐름에 영향을 주지 않는 것으로, 추적 저장이 실패해도 AI 생성 요청 자체는 정상 진행됩니다.
에이전트와 라우터 코드를 건드리지 않고 ai_service.py 단일 지점에서만 호출하도록 구성해 침습성을 최소화했습니다.
이를 통해 에이전트별 평균 레이턴시와 실패율을 비교하고, 문자 수 기반으로 모델별 토큰 사용량을 추정해 비용 구조를 가시화할 수 있게 됐습니다.
블랙박스였던 AI 실행 과정을 화이트박스로 바꾼 경험입니다.

### AI 과제 주도 / 적극성
현대위아에서 AI Agentic 시스템 개발은 제 원래 직무가 아니었습니다.
생성형 AI 활용 요구가 늘어나고 있었지만 기업 보안 정책을 만족하는 통제된 플랫폼이 없다는 문제를 먼저 발견하고, 이를 직접 과제로 제안해 AI Agent Studio PoC를 주도했습니다.
기획 부서의 지시를 기다리지 않고 현장의 비효율을 관찰한 뒤 방향을 먼저 만든 경험입니다.
> 활용 포인트: "기획을 기다리기보다 문제를 먼저 발견하고 해결하는 분" 유형의 JD에 직접 대응 가능.

### 실시간 거래형 시스템 / Click-CEO
Click-CEO 프로젝트에서 호가창 기반 실시간 주식 시뮬레이션을 개발했습니다.
주문 등록, 체결, 잔고 반영, 시세 전파가 동시에 이뤄지는 구조로, 금융 서비스와 유사한 실시간성·정합성·동시성 제어가 핵심인 환경이었습니다.
Polling 구조를 WebSocket으로 전환한 뒤 Stress Test에서 연결 실패율 44%가 발생했고, 병목 분석 후 Redis 기반 저지연 처리와 Kafka 기반 비동기 이벤트 분리로 구조를 개선했습니다.
이후 연결 실패율을 2% 미만으로 감소시켰습니다.
> 활용 포인트: 금융 도메인 무경험 우회용 소재. 실시간성·정합성 키워드 JD에 활용.

### 운영 인프라 / 무중단 배포 · 자동 스케일링
Docker로 컨테이너화하고 Kubernetes 환경에서 운영했습니다.
Jenkins CasC와 Kubernetes Rolling Update를 적용해 무중단 배포 구조를 구현했고, Kubernetes HPA를 구성해 컨테이너 리소스 사용량이 70%를 초과하면 자동으로 파드를 증설하도록 설계했습니다.
예측 불가능한 트래픽 증가에도 서비스가 흔들리지 않는 구조를 만든 경험입니다.
> 활용 포인트: Docker/K8s/CI-CD 우대 JD, 인프라·DevOps 색깔 있는 포지션.

### MCP 기반 레거시 통합 아키텍처 (PoC)
여러 레거시 시스템을 하나의 AI 에이전트로 통합할 수 있는 구조를 설계했습니다. FastAPI에 `@mcp` 데코레이터를 붙여 레거시 API 위에 Tool 이름·설명·입출력 스키마를 노출하는 MCP 서버를 구현했고, 레거시마다 API만 따로 열어두면 AI가 어떤 도구를 언제 써야 하는지 스스로 판단할 수 없다는 한계를 이 방식으로 해결했습니다. MCPLoader가 기동 시 Tool 정보를 수집해 메모리 카탈로그로 통합하고 5분 주기로 갱신하도록 설계했으며, Claude+LangGraph 기반 에이전트가 이 카탈로그에서 요청에 맞는 Tool을 자동 선택·실행하도록 구성했습니다. 새 레거시가 추가돼도 플랫폼 코드를 건드리지 않고 MCP 주소 한 줄만 등록하면 되는 느슨한 결합 구조가 핵심입니다.
실제 테스트는 제가 담당하는 MES 시스템 하나를 대상으로 로컬 환경에서 진행했고, ERP·인벤토리 등은 같은 구조로 확장 가능하도록 설계만 해둔 상태입니다. PoC 단계로 실제 운영 반영 전이며, 사내 워크샵에서 이 구조를 발표했습니다.
> 활용 포인트: 아키텍처 설계력·시스템 통합 경험, MCP/AI 인프라 관련 JD에 직접 대응 가능. (실제 검증은 MES 1개 시스템·로컬 테스트 범위였다는 것을 면접에서 정확히 밝힐 것 — 여러 시스템 통합/운영 성과로 과장 금지)

## 2. 소프트 스킬 — AX/DX & 개발자 직무 중심

### AX/DX를 대하는 개발자로서의 태도
저는 AX/DX가 도구를 얹는 일이 아니라 현장의 판단 흐름 자체를 바꾸는 일이라고 생각합니다.
현대위아에서 생성형 AI 활용 요구는 늘고 있었지만 기업 보안 정책을 만족하는 통제된 플랫폼이 없다는 문제를, 기획 부서의 지시를 기다리지 않고 먼저 발견해 AI Agent Studio PoC를 직접 과제로 제안했습니다.
개발자가 이런 전환기에 할 수 있는 역할은 요구받은 기능을 구현하는 것을 넘어, 아직 방향이 정리되지 않은 문제를 먼저 정의하고 구조로 제안하는 것이라고 생각합니다.
바이브코딩 스튜디오를 운영하며 CodeGenerator/EditAgent/SummaryAgent가 블랙박스로 실행되는 한계에 부딪혔을 때도, 기존 코드를 건드리지 않고 ai_service.py 단일 지점에서만 관측 로직을 붙이는 방식으로 AgentOps Tracer를 설계했습니다.
새로운 기술을 도입할 때 기존 구조에 대한 침습을 최소화하면서 문제를 해결하는 방식이 AX/DX 전환기 개발자에게 필요한 태도라고 생각합니다.

### 성격 — 장점
1. **원인을 끝까지 추적하는 집요함**: 문제가 생기면 화면에 보이는 증상만 고치지 않고, 데이터가 생성·전달·반영되는 흐름 전체를 먼저 따라가는 습관이 있습니다. (데이터 정합성 트러블슈팅 다수 경험 기반)
2. **지시를 기다리지 않는 주도성**: 문제를 발견하면 담당 여부와 상관없이 먼저 검증하고 과제로 제안합니다. (AI Agent Studio PoC 제안)
3. **구현하며 배우는 학습 방식**: 개념을 완전히 이해한 뒤 시작하기보다 먼저 만들어보고 그 과정에서 구조를 체득하는 방식이 익숙합니다. AI Agent 관련 지식이 없는 상태에서도 멀티 에이전트 구조 설계까지 빠르게 따라간 경험이 있습니다.

### 성격 — 단점 및 보완
**방향을 스스로 판단하고 먼저 진행하려는 성향 때문에, 실제 의도와 어긋난 방향으로 작업이 진행된 적이 있습니다.**
현대위아에서 팀장님이 "AI를 회사에 어떻게 도입하면 좋을지 발표해보라"는 요청을 주셨을 때, 저는 넓은 AI 개념 중 Figma AI를 타겟으로 잡아 화면 설계를 미리 그려 공수와 비용을 줄이자는 방향으로 발표를 준비했습니다.
하지만 팀장님의 의도는 AI Agent를 사내에 도입하기 위해 필요한 요소 — 보안, 필요 기술, 구현 방법 — 를 직접 만들어보며 파악하라는 것이었고, 방향이 어긋났다는 것을 발표 후에야 알게 됐습니다.
이 경험 이후로는 방향성이 어느 정도 잡히면 곧바로 진행하기보다, 먼저 선임에게 이 방향이 맞는지 빠르게 확인받는 습관을 갖게 됐습니다. 혼자 오래 붙잡고 있다가 틀리는 것보다, 짧게라도 먼저 맞춰보고 진행하는 것이 훨씬 효율적이라는 것을 배웠습니다.

### 갈등 경험과 해결 — 개발 관점
1. **Click-CEO, 기술 방향 이견**: polling 유지 vs WebSocket 전환으로 팀 의견이 갈렸을 때, 팀장으로서 의견을 조율하는 대신 PoC로 두 방식을 검증해 데이터를 기준으로 팀 전체의 합의를 이끌어냈습니다. 이후 문제가 생겼을 때도 방향 자체를 다시 논쟁하지 않고 같은 기준 위에서 해결책을 찾을 수 있었습니다.
2. **현대위아, 현업-협력사 프로세스 갈등**: 현업이 화면 증상만 협력사에 전달해 협력사가 엉뚱한 지점을 고치는 일이 반복되자, PM과 개발을 함께 맡고 있던 제가 이슈를 먼저 검토해 원인과 영향 범위를 정리한 뒤 전달하는 중간 프로세스를 신설했습니다. 이후 동일 이슈 재문의가 줄고 처리 시간도 단축됐습니다.
3. **애기야가자, 장애 대응 방식 이견**: 트래픽 급증 시 "서버 스펙업"을 주장하는 의견과 원인 분석이 먼저라는 제 의견이 부딪혔을 때, 로그와 쿼리 분석으로 병목 지점을 먼저 증명해 캐시 구조 개선으로 설득했습니다.
4. **현대위아, 모의해킹 대응 시 테이블 설계 이견**: 모의해킹 진단에서 URL 레벨 권한 검증이 없다는 취약점이 나왔을 때, 기존 메뉴 관리 체계를 분석해 url-role 매핑 테이블 하나로 통합하자고 제안했습니다. 시니어 개발자는 기존 테이블 구조를 고려하지 않은 설계라며 여러 테이블로 나누자는 의견을 냈고, 저는 PoC를 만들어 제 방식이 실제로 동작한다는 근거를 먼저 보여줬습니다. 동시에 시니어 개발자가 제안한 "인터셉터로 URL 호출을 수집하고 호출 횟수를 카운트해 유지보수 데이터로 쓰자"는 아이디어는 더 나은 방향이라 판단해 그대로 받아들여 구조에 반영했습니다. 근거로 설득하는 것과, 더 나은 의견은 인정하고 받아들이는 것을 같이 보여준 경험입니다.

### 리더십 · 협업 경험 — Click-CEO 팀장
SSAFY 6인 팀 프로젝트 Click-CEO에서 팀장을 맡아 우수상을 수상했습니다. 팀장의 역할은 혼자 정답을 내리는 사람이 아니라, 팀이 더 나은 결정을 내릴 수 있도록 기준을 만드는 사람이라는 것을 이 경험으로 배웠습니다.
1) **기술적 합의**: polling 유지냐 WebSocket 전환이냐로 의견이 갈렸을 때, 팀장으로서 일방적으로 정하지 않고 PoC로 두 방식을 검증해 팀 전체가 동의할 수 있는 기준을 먼저 만들었습니다.
2) **블로킹 최소화**: 개발 전에 백엔드·DE·프론트엔드가 인터페이스와 이벤트 스키마부터 합의해, 각자 독립적으로 병렬 개발하고 통합 단계에서 큰 충돌 없이 연결했습니다.
3) **전체 흐름 문제 해결**: WebSocket 전환 후 연결 실패율 44%가 발생했을 때, 배포 일정이 임박했지만 급한 조치만 하고 넘어가지 않고 팀원들과 함께 시스템 전체 흐름을 다시 따라가 봇 주문 → Redis → Kafka 구간의 병목을 찾아 실패율을 0%까지 낮췄습니다.
> 활용 포인트: 리더십/협업 성과 문항, 팀워크·리더십 강조 JD. (갈등 경험 1번과 같은 프로젝트, 관점만 리더십으로 전환)

### 실패 경험과 극복
PM 업무를 수행하며 견적서 작성, 문서 작성, 보고를 기간을 정해두고 진행했는데, 견적 금액이 실제와 맞지 않아 재요청이 발생하고 문서 작성 과정에서도 피드백 반영이 반복되면서 계획한 일정에 차질이 생긴 경험이 있습니다.
이 경험 이후로는 일정을 세울 때 항상 여유를 두고, 마감 전에 일정 부분을 미리 진행해두는 습관을 갖게 됐습니다.

### 스트레스 · 압박 상황 대처
신체적 해소와 구조적 정리, 두 가지 방식을 같이 씁니다.
- **신체적 해소**: 심호흡으로 즉시 긴장을 낮추고, 헬스·러닝·축구로 정기적으로 스트레스를 배출합니다. 몸이 지치면 판단력도 같이 떨어진다고 생각해서, 압박이 심한 시기일수록 운동 루틴은 오히려 더 지키려 합니다.
- **구조적 정리**: 할 일이 몰릴 때는 감정적으로 조급해하기보다 Planner로 작업을 작은 task 단위로 쪼갭니다. 큰 문제를 통째로 들고 있으면 압박감만 커지지만, 지금 당장 처리 가능한 단위로 나누면 무엇부터 손대야 할지 명확해집니다.
> 활용 포인트: Click-CEO 배포 임박+장애 겹친 상황(연결 실패율 44%) 같은 구체 사례와 엮어서 쓰면 좋음.

## 3. AI 활용 능력 (직무 공통 소재)

기존 "AI 역량" 섹션이 기술 구현 중심이었다면, 여기는 **AI를 도구로서 어떻게 다루는지**에 초점.
SK하이닉스 등 최근 채용에서 평가하는 5대 축(워크플로우 설계 / 명세화와 컨텍스트 / Agent 설계 / 오케스트레이션 / 검증과 반복)에 기존 경험을 매핑.

### 1) 워크플로우 설계 — 문제를 어떻게 쪼개고 순서를 짰는가
바이브코딩 스튜디오를 설계할 때 "코드 생성 → 코드 수정 → 요약"이라는 개발 흐름을 하나의 에이전트가 다 처리하게 하지 않고, CodeGenerator / EditAgent / SummaryAgent 세 단계로 명확히 쪼갰습니다. 각 단계가 서로 다른 실패 지점을 가지기 때문에, 하나로 묶으면 실패 원인을 특정할 수 없다고 판단했기 때문입니다.

### 2) 명세화와 컨텍스트 — 요구사항과 조건을 얼마나 구체적으로 정리했는가
기존 사내 시스템과 AI를 통합하기 위해 MCP 도구를 직접 구현할 때, "AI가 어떤 데이터를 조회할 수 있고 어떤 액션은 금지되는지"를 도구 스펙 레벨에서 먼저 정의했습니다. 모델에게 자연어로 지시하는 것이 아니라, 호출 가능한 도구 자체를 제한해 명세를 강제하는 방식을 택했습니다.

### 3) Agent 설계 — 반복 작업을 얼마나 구조화했는가
LangGraph로 CodeGenerator / EditAgent / SummaryAgent를 분리한 멀티 에이전트 구조를 설계했습니다. 각 에이전트가 자기 역할만 담당하고 상태를 그래프로 전달하도록 구성해, 한 에이전트의 로직을 바꿔도 다른 에이전트에 영향이 가지 않게 만들었습니다.

### 4) 오케스트레이션 — 여러 도구와 단계를 어떻게 조합했는가
Claude Agentic Loop 기반으로 에이전트가 어떤 도구를 어떤 순서로 호출할지 직접 설계했습니다. 단순 LLM API 호출이 아니라, 도구 호출 결과에 따라 다음 행동이 갈라지는 구조를 만든 경험입니다. SSAFY 프로젝트에서는 pgVector 기반 RAG 파이프라인에 영상 리사이즈 단계를 끼워 넣어 토큰 비용을 절감하는 식으로, 비용까지 고려한 파이프라인 조합을 설계했습니다.

### 5) 검증과 반복 — 결과를 기준에 대고 확인하고 고쳤는가
AgentOps Tracer가 이 축의 핵심 소재입니다. 에이전트별 응답 레이턴시, 성공 여부, 오류 메시지를 매 실행마다 기록해 "어디서 얼마나 실패하는지"를 수치로 볼 수 있게 만들었고, 그 데이터를 기준으로 에이전트별 병목을 찾아 개선했습니다. 블랙박스였던 AI 실행 과정을 화이트박스로 바꾼 경험 자체가 "검증하고 반복하는 루프를 만든 경험"입니다.

### AI 활용 습관 (프로세스 차원)
- 프롬프트로 초안을 받으면 그대로 쓰지 않고, 결과물 기준(수치, 실제 경험, 재현 가능성)으로 되돌아가 검증하는 습관
- AI가 만든 코드/구조는 반드시 실패 케이스를 직접 넣어 검증 후 반영
- 반복 작업(코드 리뷰, 요약, 문서화)은 에이전트로 위임하되, 판단이 필요한 지점(방향 결정, 리스크 평가)은 직접 개입

## 4. AX/DX 추진 시 채용해야 하는 이유

저는 현재 대기업 제조 현장(현대위아)에서 AX/DX 전환 업무를 실무로 진행하고 있습니다.
Microsoft Copilot과 Claude Code 기반 바이브코딩을 모두 실무에 적용해봤기 때문에, 특정 벤더 도구 하나에 종속되지 않고 각 도구가 어떤 업무에 적합한지 직접 비교해본 경험이 있습니다.

AX/DX 전환에서 진짜 어려운 지점은 새 AI 도구를 들여오는 것 자체가 아니라, 기존 레거시 시스템과 어떻게 연결하느냐라고 생각합니다.
단순 API 연동만으로는 AI가 시스템 상태를 판단하고 조작하기 어렵기 때문에, MCP처럼 AI가 호출 가능한 도구 단위로 레거시 기능을 재정의하는 방식이 필요하다는 것을 실제 MCP 도구를 구현하며 배우고 있습니다.

실제로 여러 레거시를 하나의 AI 에이전트로 통합할 수 있는 구조를 설계하고, FastAPI에 `@mcp` 데코레이터를 붙여 Tool 스키마를 노출하는 MCP 서버를 직접 구현했습니다. 검증은 제가 담당하는 MES 시스템을 대상으로 로컬 환경에서 진행했고, ERP·인벤토리 등은 같은 구조로 붙일 수 있도록 설계만 해둔 단계입니다.
API만 열어두는 것과 MCP로 Tool을 정의하는 것의 차이 — AI가 스스로 도구를 찾고 선택할 수 있는지 여부 — 를 이 과정에서 직접 확인했고, 아직 운영 반영 전 PoC 단계지만 이 구조를 사내 워크샵에서 발표해 공유했습니다.
레거시 쪽에서 무엇을 먼저 준비해야 AI와 연결될 수 있는지를 현장에서 직접 확인하며 익히고 있다는 점이, 이제 막 AX/DX를 시작하려는 조직에 제가 바로 기여할 수 있는 지점이라고 생각합니다.

## 5. PM 역량 — 효율화 습관

전체 흐름: 회의록 작성 → 현업 요청사항 파악 → WBS 작성 → ERP·PLC 등 연계 시스템 간 IF(인터페이스) 정의 회의. 기획으로 끝나지 않고 시스템 간 실제 연동 지점까지 직접 정의하는 것이 특징.

1. **WBS 설정**: 프로젝트 착수 시 WBS를 먼저 세워 일정과 범위를 구조화
2. **회의록 시스템 사전 검토**: 기존 회의록 양식/시스템을 먼저 검토해 템플릿을 미리 작성해두고, 있는 자료를 최대한 재사용 → 공수·비용 50% 이상 절감
3. **기존 화면 지속 검토**: 현업이 실제 쓰는 화면을 계속 확인해 요구사항과 실사용 흐름의 괴리를 줄임
4. **테이블 구조 검토**: DB 테이블 구조를 직접 확인해 기획 단계에서부터 개발 리스크를 미리 파악
5. **타 시스템 참조(수평전개)**: 유사 시스템 사례를 참조해 처음부터 새로 설계하지 않고 검증된 구조를 가져와 리스크를 줄임

**확장 사례 (실제 경험 반영)**
6. **산출물 템플릿 표준화 + 수평전개**: 회의록·WBS는 이미 템플릿화해 재사용하고 있음. 여기서 더 나아가, 현업에서 "세션을 늘려달라"는 요청이 들어왔을 때 관련 거버넌스를 찾아 현대차 쪽 세션 설정 방법을 확인·공유하고 Confluence로 문서화했습니다. 문서를 만드는 데서 끝내지 않고, 해당 내용이 RAG 자료에서 실제로 검색이 잘 되는지까지 직접 확인해 문서가 "만들어지는 것"과 "실제로 쓰이는 것"의 차이를 챙겼습니다.
7. **이슈 트래킹 체계화 — 투자비용 프로세스 문서화**: 투자 비용을 집행받을 때 필요한 투자코드·금액 전달 프로세스를 문서화하고, 어떤 코드를 전달해야 하는지도 정리해뒀습니다. HW가 전혀 없는 특수 케이스는 개발비와 공사비를 하나의 코드로 합쳐 처리하도록 별도로 문서화해, 예외 케이스까지 놓치지 않고 챙겼습니다.

8. **경량 방향 확인 습관**: 방향이 어긋나기 전에 정식 요구사항 정의서 대신 메신저 대화나 PPT 한 장 정도로 정리해 선임에게 먼저 확인받습니다. 문서 툴과 AI 요약까지 다 시도해봤지만, 결국 판단이 필요한 순간엔 한 장짜리 PPT로 핵심만 짚어 빠르게 확인받는 방식이 가장 효율적이라고 판단해 습관으로 굳혔습니다. → [성격 단점 보완] 습관과 동일 소재
9. **시스템 간 IF(인터페이스) 정의 회의**: 현업 요청사항을 파악하고 WBS를 세우는 데서 그치지 않고, ERP·PLC 등 연계 시스템과 데이터를 주고받는 지점을 직접 정의하는 인터페이스 회의를 진행했습니다. 어떤 시스템이 어떤 데이터를 언제 주고받는지 기획 단계에서 미리 맞춰둬야, 개발 단계에서 연계 오류로 되돌아가는 일을 막을 수 있다고 판단했기 때문입니다.
