[데이터 정합성 설계]
데이터 오류가 곧 현장 판단 오류로 이어지는 제조 환경에서, 화면에 보이는 증상이 아니라 데이터가 흐르는 전체 구간을 추적하는 방어적 개발을 체득했습니다. 현대위아에서 로봇·생산·품질 데이터가 여러 시스템에 얽힌 운영 환경을 다루며, 같은 증상이라도 원인이 담당 시스템이 아닌 다른 시스템의 중간 처리 로직에 있는 경우를 다수 겪었고, 방치하면 품질 이력 추적 실패 같은 실제 운영 문제로 이어졌습니다. 이후 데이터가 생성·전달·반영되는 흐름 전체를 먼저 확인하고, 문제 발생 시 원인을 빠르게 좁힐 수 있도록 로그와 예외 처리를 함께 설계하는 방식으로 개발해왔습니다. 이 습관을 갖춘 뒤로는 비슷한 유형의 장애가 재발했을 때 원인을 특정하는 데 걸리는 시간을 눈에 띄게 줄일 수 있었습니다.

[대규모 트래픽 대응]
트래픽이 급증하는 상황에서 병목을 구조적으로 진단하고 해결하는 역량을 갖췄습니다. 장소추천 플랫폼 운영 중 이벤트로 트래픽이 몰려 메인·이벤트 페이지 응답이 지연되고 이탈률이 높아지자, 병목 구간을 직접 분석해 반복 조회되는 데이터를 Redis 캐시로 분리하고 일부 데이터를 DynamoDB로 이관해 응답 속도를 유의미하게 개선했습니다. 기능 구현을 넘어 어떤 로직을 어떤 저장소로 분리해야 하는지 구조적으로 판단하는 것이 서비스 안정성을 결정한다는 것을 이 경험으로 확인했고, 이후 유사한 이벤트가 있을 때도 같은 구조를 재사용해 트래픽 급증에 선제적으로 대응하고 있습니다.

[무중단 인프라 운영]
트래픽 변동에도 흔들리지 않는 인프라를 직접 설계·운영한 경험이 있습니다. Docker로 컨테이너화하고 Kubernetes 환경에서 Jenkins CasC와 Rolling Update로 무중단 배포 구조를 구현했고, 리소스 사용량이 70%를 넘으면 자동으로 파드를 증설하는 HPA를 구성해 예측 불가능한 트래픽 증가에도 서비스 중단 없이 대응할 수 있는 구조를 만들었습니다. 배포 시점에 사용자가 서비스 중단을 체감하지 않도록 만든 것이 이 작업의 핵심 성과입니다.

[레거시 시스템 통합]
여러 레거시 시스템을 하나의 구조로 느슨하게 통합하는 설계 경험도 있습니다. FastAPI에 Tool 스키마를 노출하는 MCP 서버를 직접 구현해, 담당하는 MES 시스템을 대상으로 새 시스템이 추가돼도 플랫폼 코드를 건드리지 않고 주소 한 줄만 등록하면 되는 구조를 검증했습니다. 레거시마다 API만 따로 열어두는 방식의 한계를, 도구 단위로 통합하는 접근으로 해결한 경험이며, ERP·인벤토리 등 다른 레거시 시스템도 같은 구조로 확장할 수 있도록 설계해 뒀습니다.

[현업-개발 인터페이스 기획]
개발뿐 아니라 기획 단계에서 시스템 간 연계 지점을 직접 정의하는 역할도 수행해왔습니다. PM 업무를 겸하며 회의록 작성과 현업 요청사항 파악, WBS 수립에 그치지 않고 ERP·PLC 등 연계 시스템 간 데이터 흐름을 정의하는 인터페이스 회의를 직접 진행했습니다. 어떤 시스템이 어떤 데이터를 언제 주고받는지 기획 단계에서 미리 맞춰둬야 개발 단계에서 연계 오류로 되돌아가는 일을 막을 수 있다고 판단했기 때문이며, 이때 정리한 인터페이스 정의는 이후 유사 연계 작업의 기준 문서로도 활용되고 있습니다.

[오픈소스 기여를 통한 지속 성장]
사내 시스템 밖에서도 낯선 코드베이스를 스스로 파악해 문제를 해결하는 역량을 검증하고 싶어 오픈소스 기여를 진행하고 있습니다. 참고문헌 관리 프로그램 JabRef에서 "PDF 인덱싱 실패 시 어떤 파일이 문제인지 로그로 알 수 없다"는 이슈(#15680)를 맡아, 먼저 CONTRIBUTING 문서와 기존 이슈·PR 스레드를 정독해 프로젝트가 요구하는 코딩 컨벤션과 리뷰 절차를 파악했습니다. 이후 인덱싱과 예외 처리가 일어나는 코드 흐름을 직접 추적해 문제 지점을 좁혔고, 예외 발생 시 파일명과 citation key를 함께 기록하도록 로깅 로직을 구현해 PR로 기여하는 작업을 진행 중입니다. 담당 업무가 아닌 낯선 언어·도메인의 대규모 코드베이스라도, 문서와 코드를 근거로 스스로 구조를 파악하고 프로젝트 컨벤션에 맞춰 기여할 수 있다는 것을 확인해가는 과정입니다.

데이터의 생성부터 흐름, 인프라, 시스템 통합, 기획까지 전 구간을 직접 다뤄온 경험을 바탕으로, 데이터가 곧 현장 판단의 기준이 되는 SK하이닉스의 대규모 시스템 환경에도 바로 기여하겠습니다.


[문항 2] AI를 활용한 프로젝트/공모전/논문/연구/문제 해결 경험 등을 작성해 주세요. (2000자)
※ 필수 반영: 경험(구체적 내용) / 역할(본인이 실제로 한 일) / 기간(수행 기간). 단순 질의응답 활용 사례는 지양.

[기간: 20XX년 X월 ~ X월, 약 X개월 — 실제 기간 확인 후 채워 넣을 것]
현대위아에서 생성형 AI 활용 요구는 늘고 있었지만 기업 보안 정책을 만족하는 통제된 플랫폼이 없다는 문제를 먼저 발견했습니다. 담당 업무가 아니었음에도 이를 과제로 직접 제안했고, 기획부터 설계, 구현, 배포까지 전 과정을 제가 전담해 AI Agent Studio를 만들었습니다.

먼저 "코드 생성 → 수정 → 요약"으로 이어지는 개발 흐름을 하나의 에이전트가 다 처리하게 두지 않고, 제가 CodeGenerator·EditAgent·SummaryAgent 세 단계로 직접 쪼갰습니다. 각 단계가 서로 다른 실패 지점을 갖기 때문에 하나로 묶으면 실패 원인을 특정할 수 없다고 판단했기 때문입니다. LangGraph로 이 세 에이전트를 상태 그래프로 연결하는 구조 설계와 구현을 맡아, 한 에이전트의 로직을 바꿔도 다른 에이전트에 영향이 가지 않게 만들었습니다. 기존 사내 시스템과 통합할 때는 자연어로 지시하는 대신, AI가 어떤 데이터를 조회할 수 있고 어떤 액션은 금지되는지 도구 스펙 레벨에서 정의하는 MCP 도구를 제가 직접 구현해 명세를 강제했습니다. Claude Agentic Loop 기반으로 에이전트가 어떤 도구를 어떤 순서로 호출할지도 직접 설계해, 호출 결과에 따라 다음 행동이 갈라지는 구조를 만들었습니다.

운영 중 곧 한계에 부딪혔습니다. 세 에이전트가 순차 실행되는 구조에서 실패가 나면 어느 단계에서 얼마나 걸렸는지, 토큰이 어디서 소비됐는지 로그를 직접 뒤져야 했고, AI 추론 과정 자체가 블랙박스였습니다. 저는 이를 해결하기 위해 에이전트 실행 전반을 추적하는 AgentOps Tracer를 혼자 설계하고 구현했습니다. 에이전트명, 사용 모델, 응답 레이턴시, 입출력 문자 수, 성공 여부와 오류 메시지를 매 실행마다 기록하되, 추적 저장이 실패해도 AI 생성 요청 자체는 영향받지 않도록 ai_service.py 한 지점에서만 호출해 침습성을 최소화하는 설계를 직접 결정했습니다. 그 결과 에이전트별 레이턴시와 실패율을 비교하고 문자 수 기반으로 모델별 비용 구조까지 가시화할 수 있게 됐고, 블랙박스였던 실행 과정을 화이트박스로 바꿀 수 있었습니다.

AI Agent Studio의 멀티 에이전트 구조를 더 확장해, 여러 레거시 시스템을 하나의 AI 에이전트로 통합하는 아키텍처도 제가 직접 설계했습니다. API만 열어두면 AI가 언제 어떤 도구를 써야 할지 스스로 판단할 수 없다는 한계를, Tool 스키마를 노출하는 MCP 서버와 5분 주기로 갱신되는 Tool 카탈로그로 해결했습니다. 담당하는 시스템 한 곳을 대상으로 로컬 검증까지 마쳤고, 사내 워크샵에서 이 구조를 직접 발표해 공유했습니다.

[기간: 현재까지 유지보수 진행 중]
AI가 준 결과를 그대로 받아들이지 않고 검증하는 것도 중요한 역량이라고 생각합니다. 현재 담당하는 TMS MES 시스템 유지보수에 Copilot을 활용하고 있는데, 보안 점검에서 나온 URL 권한 검증 이슈를 처리할 때 Copilot은 기능별로 3개의 테이블을 나눠 만들 것을 제안했습니다. 그대로 적용하지 않고 기존 메뉴별 권한 관리 테이블 구조를 먼저 파악한 뒤, Copilot의 제안과 기존 구조를 비교해 하나의 테이블로 매핑해 통합했습니다. AI의 제안이 더 간단해 보여도 기존 코드베이스 구조와 맞지 않으면 그대로 쓰지 않고 직접 검토한 뒤 판단해야 한다는 것을 이 경험으로 체득했습니다.

[기간: 진행 중]
오픈소스 프로젝트 JabRef 이슈(#15680) 기여를 준비하며, 처음 다뤄보는 대규모 Java 코드베이스를 분석하는 데 AI를 활용했습니다. 이슈에는 재현 절차와 결과 로그만 있고 원인이 되는 코드 위치는 나와 있지 않아, AI에게 인덱싱 실패 시 예외가 발생하는 지점과 관련 클래스 간 호출 흐름을 함께 추적하도록 질의해 코드베이스 구조를 파악하는 시간을 단축했습니다. AI가 짚어준 지점을 그대로 적용하지 않고 실제 코드를 직접 읽어 예외 처리 흐름과 일치하는지 검증했고, 이를 바탕으로 파일명과 citation key를 로그에 남기는 구체적인 구현 방향은 제가 직접 정해 작업하고 있습니다. AI를 코드를 대신 짜주는 도구가 아니라 낯선 코드베이스를 탐색하는 지도로 활용하고, 최종 판단과 구현 검증은 직접 맡는 방식이 처음 접하는 프로젝트에서도 유효하다는 것을 이 과정으로 다시 확인했습니다.

AI에게 질문해서 답을 받는 것과, AI가 안정적으로 판단할 수 있는 구조를 직접 설계하는 것, 그리고 AI가 준 결과를 검증해 실제 구조에 맞게 고치는 것은 모두 다른 역량이라는 것을 이 과정들로 확인했습니다. 앞으로도 AI를 도구로 얹는 데 그치지 않고, AI가 신뢰성 있게 동작할 수 있는 구조를 만들고 그 결과를 검증하는 역할을 하고 싶습니다.
